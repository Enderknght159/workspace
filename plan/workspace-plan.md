# Workspace — دراسة نظام تشغيل المكتب الإعلامي

> **النسخة:** 2.0 — وثيقة الاتفاق النهائية
> **التاريخ:** 2026-11-04
> **الحالة:** قرارات معتمدة، جاهزة للتنفيذ
> **النطاق:** تطبيق ديسكتوب + OpenCode + إدارة تخزين وأرشيف + تحقق بشري
> **ملاحظة:** القياسات المذكورة عن العتاد هي لجهاز التطوير الحالي، وليست جهاز المكتب الإعلامي.

---

## 0. هوية المنتج والقرارات المعتمدة

### الاسم

- **المنتج:** `Workspace`
- **الشعار:** «كل المكتب في نافذة واحدة»
- **التنفيذي:** `Workspace.exe` (لاتيني دائمًا، لتجنّب مشاكل المسارات والسجلات)
- **الواجهة:** عربية RTL، والاسم يظهر لاتينيًا كعلامة.

**ملاحظة تسمية:** كلمة `Workspace` عامة ومستخدمة تجاريًا (Google Workspace وغيرها). لا مشكلة داخليًا؛ إن تقرر التوزيع لاحقًا تُراجع العلامة والنطاق قبل الاعتماد.

**فصل المصطلحات (مهم):** لتفادي الالتباس بين اسم المنتج ومفهوم «مساحة العمل»، فإن الوعاء المحمول الذي يحوي قاعدة البيانات والإعدادات يُسمى **«المكتب» (Office)** في الواجهة، و`office` في الكود وقاعدة البيانات. المنتج `Workspace` يحتوي عدة «مكاتب» إن لزم.

### جدول القرارات

| # | القرار | التفصيل |
|---|---|---|
| 1 | **تطبيق ديسكتوب** | Electron + React + TypeScript. لا نسخة ويب. نافذة واحدة مضبوطة. |
| 2 | **محرّك معزول** | قاعدة البيانات والطابور والعمليات في وحدة لا تستورد Electron، قابلة للتشغيل headless. |
| 3 | **Tray** | إغلاق النافذة يخفي التطبيق. الخروج من التري فقط، ولا خروج أثناء وظيفة نشطة. |
| 4 | **مكتب محمول** | مجلد واحد فيه قاعدة البيانات والإعدادات والأساليب، ينتقل بين الأجهزة. |
| 5 | **لا تضمين أدوات** | لا ffmpeg/Python/Whisper/Remotion/نماذج داخل التطبيق. |
| 6 | **فحص بيئة وتجهيز موجّه** | Doctor عند أول تشغيل + OpenCode يثبّت الناقص بموافقة. التعريفات وCUDA تُشخَّص ولا تُثبَّت آليًا. |
| 7 | **هوية أقراص مركّبة** | بصمة مخفية + Volume GUID + Serial، ومسارات نسبية `(volume_id, rel_path)` فقط. |
| 8 | **صلاحيات بكلمة مرور** | لا أدمن. تسجيل دخول اختياري. إجراءات مقفلة بكلمة مرور المكتب لمدة 10 دقائق. |
| 9 | **أساليب كحزم بيانات** | `style.json` + قالب طلب + قائمة تحقق + وصفات (Recipes). لا منطق أسلوب في الكود. |
| 10 | **جدولة ليلية** | طابور دائم، استئناف بعد إعادة التشغيل، منع النوم، تقرير صباحي. |
| 11 | **بريمير يبقى** | الوضع الافتراضي يدوي، والمساعد (Rough Cut/Markers/Proxies) أولوية قبل التلقائي الكامل. |
| 12 | **حسابات محلية** | كل الحسابات على نفس الجهاز. لا مزامنة سحابية. |

### قرارات تكميلية اعتمدت افتراضيًا

- لا تبدأ الوظائف الآلية قبل أن يصبح فحص البيئة أخضر. الوظائف اليدوية مسموحة مع تحذير.
- مهلة الصلاحية المرتفعة: **10 دقائق**.
- إصدار الأسلوب وهاش الحزمة يُسجّلان في كل وظيفة.

## 1. الملخص التنفيذي

**الحكم:** الفكرة سليمة وقابلة للبناء، لكنها ليست «إضافة زر إلى الواجهة الحالية». الفجوة ليست في الذكاء الاصطناعي، بل في **طبقة التشغيل** المحيطة بالملفات: هوية الأصل، حالته، طابوره، من راجعه، وأين نسخته المؤرشفة. ابنِ هذه الطبقة، وسيصبح OpenCode مجرد **منفّذ** يمكن استبداله.

المبادئ الستة الحاكمة:

1. **افصل الحدث عن الوظيفة عن المهمة البشرية.** الدرس/الفعالية = حدث. المونتاج/النشر = وظيفة آلية. من فعل ماذا = مهمة بشرية.
2. **قاعدة البيانات مصدر الحقيقة، والمجلدات انعكاس لها.** مع مُصالِح يكتشف انحراف المستخدمين في Explorer.
3. **الوكيل لا يلمس الملفات.** يقرأ ويكتب داخل مساحة عمل محددة، والنقل/الحذف/الأرشفة تنفّذها الخدمة بعد تحقق.
4. **الأتمتة الكاملة = مسودة، لا نشر.** بوابة مراجعة بشرية إلزامية.
5. **الوضع الافتراضي يدوي، والأزرار الآلية إضافية** تُظهر الوقت المتوقع وتُعطّل نفسها بسباب مفهوم.
6. **المنتج محايد وقابل لإعادة الاستخدام.** لا مسار ثابت، لا اسم مسجد في الكود، لا افتراض GPU.

**التقدير الواقعي:** MVP في **6–8 أسابيع** عمل متقطع، والنسخة الكاملة **9–13 أسبوعًا**. الفاعلية: خفض **40–60%** من الوقت البشري في أول 3 أشهر، و**60–70%** بعد التوليف.

## 2. تشخيص الوضع الحالي

راجعنا التطبيق `mosque-media-office`: واجهة عربية RTL، SPA بلا إطار، تخزين في `localStorage`، تصدير/استيراد JSON وExcel، قفل بكلمة مرور، وضع تجريبي، وتغليف إلى `.exe` واحد عبر Node SEA.

### ما يُحتفظ به

- اللغة البصرية ومنطق RTL والوضع الليلي والاستجابة للجوال.
- نموذج المراحل (Stages) القابل لإعادة الاستخدام في خط الإنتاج.
- تصدير/استيراد JSON كمسار ترحيل.
- فكرة التغليف إلى ملف واحد.

### لماذا لا يُبنى فوقه مباشرة

| الاحتياج | الوضع الحالي |
|---|---|
| معرفة مكان الملف على القرص | غير موجود |
| قاعدة بيانات مشتركة بين الواجهة والعمال | `localStorage` في متصفح واحد |
| API خلفي | لا يوجد؛ الخادم يقدّم ملفات ثابتة |
| مهام خلفية / طابور | لا يوجد |
| حالة الملف (todo/in progress/done/output/archive) | لا يوجد |
| سجل تدقيق | لا يوجد |
| أرشفة وهارد خارجي وتحقق سلامة | لا يوجد |
| تفريغ بطاقة ذاكرة | لا يوجد |
| تعامل مع فيديو/صوت/صور | لا يوجد |

**القرار:** المشروع الجديد يُبنى من الصفر كتطبيق ديسكتوب. يُنقل من القديم: الهوية البصرية، نماذج المراحل، وبيانات المستخدمين/المهام عبر تصدير JSON. لا يُعاد استخدام كود التخزين أو الواجهة كما هو.

## 4. المنصة: تطبيق ديسكتوب

### لماذا ديسكتوب

- نوافذ أصلية لاختيار المجلدات، وسحب وإفلات من Explorer.
- أيقونة صينية، تشغيل تلقائي، إشعارات نظام، نسخة واحدة.
- تجربة واحدة بلا متصفح ولا `localhost` ولا التباس «هل الخادم يعمل؟».
- تحكم كامل في شكل الواجهة، وهو مطلب صريح.

### Electron أم Tauri

| | Electron | Tauri |
|---|---|---|
| الحجم | 100–150MB | 10–20MB |
| RAM إضافي | 250–400MB | 80–150MB |
| الخلفية | JS/TS | Rust (+ sidecar غالبًا) |
| نضج أدوات الملفات/ffmpeg | ممتاز | جيد |
| سهولة البناء والتشخيص | عالية | متوسطة |
| التحديث التلقائي | ناضج | جيد لكن خطوات أكثر |

**الاختيار: Electron + React + TypeScript.** الـ300MB لا تعني شيئًا أمام ffmpeg وRemotion. Tauri يصبح منطقيًا فقط لو صار الحجم الصغير شرطًا، وحينها ستحتاج sidecar بـNode على أي حال.

### قواعد عملية

- **نسخة واحدة فقط** (single instance)؛ لا تفتح نسختان على نفس قاعدة البيانات.
- **Tray دائم:** إغلاق النافذة يخفيها. الخروج من قائمة التري.
- **منع الخروج أثناء وظيفة نشطة:** يعرض «إيقاف بعد الحالية / إلغاء الوظيفة / البقاء».
- **منع النوم** أثناء الوظائف.
- **تحديث تلقائي** من مجلد محلي أو GitHub Releases. بدون توقيع كود سيظهر تحذير SmartScreen عند أول تشغيل؛ هذا طبيعي داخليًا.
- **وضع محمول** (Portable) بجانب الوضع المثبّت إن رغبت.

## 5. نموذج المجالات

| الكيان | الوصف | الحقول الأساسية |
|---|---|---|
| `volumes` | قرص داخلي/خارجي | `id, volume_guid, serial, label, kind(hot/cold), capacity, free, last_seen, status` |
| `events` | درس، خطبة، فعالية، جلسة تصوير | `id, kind, title, title_slug, occurred_at, state, owner_id` |
| `assets` | ملف مصدر أو ناتج | `id, event_id, sha256, volume_id, rel_path, kind, bytes, duration, width, height, captured_at, status` |
| `jobs` | وظيفة آلية أو يدوية | `id, event_id, kind, mode, style_id, style_version, state, priority, attempts, agent_session_id, workspace_rel, result_json, error, machine_id` |
| `styles` | سجل أساليب المونتاج | `id, name, skill_id, version, params_schema, est_minutes, gpu, preview_path, enabled` |
| `recipes` | وصفة الحدث | `event_kind, jobs[]` |
| `reviews` | قرارات بشرية | `id, job_id, reviewer_id, decision, checklist_json, notes, created_at` |
| `publications` | أين نُشر | `id, job_id, platform, url, published_at, published_by` |
| `placements` | أين توجد نسخة الأصل | `asset_id, volume_id, rel_path, role(primary/replica)` |
| `archive_moves` | سجل النقل | `id, asset_id, from_volume, to_volume, rel_path, sha256, verified_at` |
| `audit_log` | من فعل ماذا | `id, actor_id, action, entity, entity_id, before, after, at, elevated` |

### لماذا فصل `events` عن `jobs`

الدرس الواحد ينتج: فيديو كامل، 3 ريلز، غلافًا، وترجمة. الوضع القديم (مهمة واحدة بحالة واحدة) يجبرك على تكرار الدرس. الفصل يسمح بأن يكون **الحدث** في `in_progress` بينما **ريل منه** في `review` وآخر في `published`.

### العلاقة بالمهام البشرية

تبقى جداول `users / templates / groups / tasks / stages` للعمل البشري (من صوّر، من راجع). تُربط بـ`event_id`. لا تُخلط سجلات البشر بسجلات الآلات.

## 6. آلة الحالة

### على مستوى الحدث

```
draft → ingested → todo → in_progress → edited → in_review → approved → published → archived → cold
                                   ↘ blocked            ↘ rejected → in_progress
```

### على مستوى الوظيفة

```
queued → running → succeeded → review_pending → approved → published → archived
   ↘ cancelled        ↘ failed (retry ≤ 2)        ↘ rejected → revision job
   ↘ blocked (شروط ناقصة)   ↘ blocked_offline (قرص غير موصول)
```

**قواعد صارمة:**

- لا `published` دون `reviews.decision = approved`.
- لا `archived` مع وظيفة مفتوحة أو نشر غير مكتمل.
- لا `cold` دون تحقق هاش + كتالوج على القرص الهدف.
- `blocked_offline` ليس فشلًا؛ يُستأنف تلقائيًا عند توصيل القرص.
- `failed` لا يعني `done`، ولا يُتجاوز يدويًا إلا بسبب مسجّل.

## 7. عقد التخزين والمسارات

### الشجرة المقترحة

```
<HotRoot>\WorkspaceData\
  00_inbox\                          ← هبوط البطاقة، لا يُعدّل
    20261104_card-A7IV\
  10_events\
    2026\11\
      20261104_lesson_abu-bakr\
        manifest.json
        source\      ← الأصول الأصلية (قراءة فقط)
        work\        ← مساحة الوكيل
        output\      ← التسليمات
        review\      ← contact sheet ولقطات المراجعة
  20_photos\
    2026\11\
      20261103_event_iftar\
        originals\
        selects\
  80_archive\
  90_trash\                          ← 30 يومًا قبل الحذف
```

الهارد البارد مرآة:

```
<ColdRoot>\WorkspaceCold\
  catalog.json
  10_events\2026\11\...
```

### قواعد التسمية

- **المسار دائمًا ASCII:** `20261104_lesson_abu-bakr`.
- **العنوان العربي في قاعدة البيانات و`manifest.json`**، لا في اسم المجلد.
- التاريخ `YYYYMMDD` في البداية لضمان الترتيب.
- `slug` بأحرف لاتينية صغيرة وأرقام وشرطات، بحد أقصى 40 حرفًا.

**السبب:** مهارة المونتاج نفسها تحذّر من ترميز العربية في PowerShell، وRemotion/ffmpeg/JSON أكثر هشاشة مع المسارات العربية. فصل «اسم العرض» عن «مسار التخزين» يحل المشكلة نهائيًا.

### `manifest.json`

```json
{
  "schema": 1,
  "event_id": "evt_01J...",
  "kind": "lesson",
  "title": "درس: بر الوالدين",
  "occurred_at": "2026-11-04",
  "state": "in_review",
  "jobs": [{ "id": "job_...", "kind": "edit", "style": "mreel1", "state": "succeeded" }],
  "assets": [{ "sha256": "...", "path": "source/main.mp4", "kind": "video" }]
}
```

### قاعدة المسارات المطلقة

> **لا يُخزَّن أي مسار مطلق في قاعدة البيانات. يُخزَّن `(volume_id, rel_path)` فقط، ويُشتق المسار وقت التشغيل.**

هذه القاعدة وحدها تجعل المكتب محمولًا، وتجعل تغيّر حرف القرص بلا أثر.

## 8. هوية الأقراص والأرشيف

### ملف البصمة

عند تسجيل قرص يُكتب في جذره:

```
<Root>\.workspace-office\
   volume.json      ← volume_id + label + schema + offices[]
   catalog.jsonl    ← فهرس append-only
   checksums\
```

مع `attrib +h +s` لإخفائه.

### الهوية المركّبة

| الإشارة | المصدر | لماذا |
|---|---|---|
| `volume_id` | ملف البصمة | يتحكم به التطبيق، وينجو من تغيير الحرف |
| **Volume GUID** | `Get-Volume` / `mountvol` (`\\?\Volume{...}\`) | مستقر داخل نظام الملفات، مستقل عن الحرف |
| Serial + الحجم + نوع FS | `fsutil fsinfo volumeinfo` | احتياطي عند فقدان الملف |
| Partition GUID | `Get-Partition` | يميز الأقراص المتشابهة |

### خوارزمية التوصيل

```
1. امسح كل الأقراص الموصولة وابحث عن .workspace-office\volume.json
2. طابق volume_id ثم الإشارات الفيزيائية:
   ├─ البصمة + GUID يطابقان       → متصل
   ├─ البصمة موجودة + GUID مختلف  → نسخة على قرص آخر → قراءة فقط + تنبيه
   ├─ البصمة مفقودة + GUID يطابق  → بصمة مفقودة → اقترح إعادة التسجيل
   ├─ بصمة غير معروفة             → قرص جديد → سجّل أو استورد
   └─ لا شيء                      → قرص غريب → لا تلمسه
3. لا اختيار بالحرف. لا fallback صامت.
```

**ملاحظة واقعية:** أي بصمة يمكن نسخها مع الملفات. لذلك لا نَعِد بكشف «الاستنساخ» بحد ذاته، بل بكشف **تعارض البصمة مع الهوية الفيزيائية** — وهو السيناريو الواقعي (نسخ مجلد إلى قرص آخر).

### تعدد الأقراص

- `role(hot/cold)`، و`placements` يسمح بنسخة ساخنة ونسخة باردة لنفس الأصل.
- القرص غير الموصول = `blocked_offline`، لا `failed`.
- الهارد البارد يعمل **read-only** افتراضيًا، ولا يُكتب إلا عند «دفعة أرشفة» صريحة.
- لا تعتمد على `exFAT` للأرشيف (بلا journaling). الأفضل NTFS، و16–20% مساحة حرة دائمة.

### خوارزمية الأرشفة الآمنة

```
1. المرشحون: state=published و published_at < now-7d و لا وظائف مفتوحة
2. انسخ (لا تنقل) إلى 80_archive بنفس المسار النسبي
3. تحقق: العدد + الحجم + sha256 لكل ملف
4. حدّث catalog.json + archive_moves + placements
5. انقل المصدر إلى 90_trash (30 يومًا)
6. احذف نهائيًا فقط بموافقة بشرية أو سياسة موقّعة
```

### سياسة المساحة

| الحد | الإجراء |
|---|---|
| أقل من 60GB | تحذير في الواجهة |
| أقل من 40GB | منع بدء مونتاج جديد |
| أقل من 25GB | تنظيف `90_trash` + اقتراح أرشفة |

## 9. بيئة التشغيل: لا تضمين، بل فحص وتجهيز

### ما يُشحن مع التطبيق

- التطبيق نفسه (~150MB).
- **إعلان متطلبات** صغير `requirements.json` — بيانات لا أدوات.
- مهارة/قالب `setup` نصي يستخدمه OpenCode.
- **Doctor** للفحص.

### ما لا يُشحن

ffmpeg، Python، Whisper، النماذج، Remotion، CUDA، أي تعريفات. الأدوات تختلف إصداراتها بين الأجهزة، وخصوصًا ما يتعلق ببطاقة الشاشة.

### ترتيب أول تشغيل

```
1. فحص OpenCode: مثبّت؟ مسجّل الدخول لمزوّد؟
   ├─ لا → دليل تثبيت/تسجيل (لا يمكن للوكيل أن يثبّت نفسه)
   └─ نعم ↓
2. OpenCode يشغّل setup: تفحص وتثبّت الناقص
   - تسأل قبل أي تنزيل > 50MB
   - قابلة للاستئناف إذا فشلت
   - تكتب سجلًا لكل خطوة
3. Doctor يتحقق فعليًا لا وجوديًا
4. تُحفظ machine_profile.json وتُفتح الواجهة
```

### فحوص Doctor

| القدرة | الفحص | معيار النجاح |
|---|---|---|
| ffmpeg | `ffmpeg -version` + `-filters` | إصدار ≥ 6.1 + `xfade/subtitles/drawtext/overlay/cropdetect` |
| Python | `python --version` | ≥ 3.10 |
| GPU | `nvidia-smi` | موجود + VRAM كافية |
| CUDA/PyTorch | `torch.cuda.is_available()` | `True` |
| Whisper | استيراد + نموذج | `large-v3` موجود |
| Remotion | `npx remotion versions` | 4.x |
| OpenCode | `opencode --version` + `/api/info` | متصل |
| بريمير | المسار + MCP | يعمل |

### استثناء صريح

**تعريف بطاقة الشاشة وCUDA لا يثبّتهما OpenCode.** تثبيت تعريفات GPU آليًا خطر. الـDoctor يعرض الحالة (`RTX 2050 — 4GB — Driver 610.62`) ويفتح صفحة NVIDIA الرسمية، ولا يثبّت.

### تفاصيل عملية

- على 4GB VRAM، الـDoctor يقترح `int8_float16` تلقائيًا (كما تنص المهارة).
- `machine_profile.json` لكل جهاز: المسارات، الإصدارات، نتيجة الفحص الفعلي.
- كل وظيفة تسجّل `machine_id` وإصدارات الأدوات.
- إن تغيّر إصدار أداة بين وظيفتين: تحذير «تغيّرت البيئة، النتائج قد تختلف».
- لا تبدأ الوظائف الآلية قبل أن يصبح الفحص أخضر. اليدوي مسموح مع تحذير.

### الصلاحيات عند إنشاء الجلسة


**تحذير صريح:** قواعد `shell` ليست صندوقًا رمليًا. الحدود الحقيقية:
1. نسخة احتياطية دائمة من `source/`.
2. منع أوامر الحذف صراحة (`del`, `rm`, `format`, `Remove-Item`).
3. لاحقًا: مستخدم Windows منفصل بصلاحيات NTFS على مجلد واحد.
4. لا `--auto` مع محتوى غير موثوق.

### التقدّم والإلغاء وإعادة المحاولة

- **التقدّم:** اشترك في `/api/event` وفلتر أحداث الجلسة؛ اربط `session.tool.called` بخطوات مفهومة.
- **الإلغاء:** `POST /api/session/{id}/interrupt` ثم تنظيف `work/`.
- **المهلة:** 120 دقيقة للمونتاج، 20 للتفريغ.
- **إعادة المحاولة:** مرة تلقائيًا مع إرفاق الخطأ، ثم توقف وطلب تدخل.
- **السجل:** احفظ `agent_session_id` واربط الواجهة بالجلسة.

### الطابور

- عامل واحد للـGPU، ويمكن عاملان للمهام الخفيفة (تفريغ/فهرسة).
- أولوية + نافذة ليلية.
- استئناف بعد إعادة التشغيل.
- قفل GPU حقيقي (ملف قفل + تحقق من العملية).

## 14. الحسابات والصلاحيات

### النموذج

- كل الحسابات على نفس الجهاز. لا سحابة.
- **تسجيل الدخول اختياري** كما في الواجهة الحالية: تختار «من أنت؟» من قائمة.
- **لا حساب أدمن.** بعض الإجراءات مقفلة بـ«كلمة مرور المكتب»، وأي حساب يستطيع الوصول إليها بها.

### الوضع المرتفع (Elevation)

- `settings.elevation` تحفظ هاش فقط.
- الإجراءات الموسومة `requires_elevation` تطلب الكلمة مرة واحدة، ثم تفتح نافذة **10 دقائق**.
- كل استخدام يُسجّل: من، متى، أي إجراء، من أي شاشة.

### الإجراءات المقفلة

| الإجراء | السبب |
|---|---|
| تعديل الأعضاء الحاليين أو حذفهم | حفظ سجل «من فعل ماذا» |
| بيانات المنصة والإعدادات العامة | تمسّ كل الفريق |
| حذف/أرشفة نهائية | لا رجعة |
| اعتماد النشر النهائي | حماية المحتوى |
| تعديل الأساليب أو مسارات التخزين | تُفسد النظام لو أُسيء |

### الأمان بصدق

كلمة مرور مشتركة على جهاز مشترك تحمي من **الخطأ**، لا من **الخائن**. من يعرفها يستطيع كل شيء. لذلك:

- `scrypt` المدمج (`N=2^15, r=8, p=1`).
- 5 محاولات كل 10 دقائق، ثم تهدئة تصاعدية.
- **رمز استرداد** يُعرض مرة واحدة ويُحفظ خارج الجهاز. لا بريد ولا «نسيت كلمة المرور».
- **قفل خمول** بعد 10 دقائق يعيد شاشة «من أنت؟».
- سجّل المستخدم النشط + من رفع الصلاحية دائمًا.

### لماذا يبقى الدخول اختياريًا

لأن الفريق صغير والجهاز واحد. أضف **تبديل مستخدم سريع** وقفل خمول؛ تحصل على التدقيق بلا احتكاك.

## 16. تفريغ البطاقة والصور

### البطاقة

1. اكتشاف المجلد الجديد بالرقم التسلسلي.
2. نسخ بـ`robocopy /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ` إلى `00_inbox/<batch_id>/`.
3. تحقق: العدد + الحجم + هاش.
4. تصنيف مبدئي: فيديو/صوت/صورة.
5. كشف التكرار بالهاش مقابل الكتالوج.
6. اقتراح اسم الحدث وتاريخه؛ المستخدم يوافق.
7. نقل إلى `source/` أو `originals/`.
8. **لا تمسح البطاقة ولا تكتب عليها.** شارة «تم التفريغ والتحقق».

### تفاصيل Windows

- مسارات > 260: Long Paths أو `\\?\`.
- `R:2 W:2` للبطاقات البطيئة؛ إعادة المحاولة أرخص من ملف تالف.

### الصور

- `20_photos/YYYY/MM/YYYYMMDD_event_slug/` مع `originals/` و`selects/`.
- تجميع بـEXIF `DateTimeOriginal`.
- إزالة التكرار بالهاش.
- **الاختيار البشري يبقى بشريًا.** اقترح فقط (blur/عيون مغلقة) ولا تحذف.

| الكابشنز | 70–85% | مراجعة شرعية/لغوية |
| المونتاج الكامل | 50–70% | يعتمد على الأسلوب |
| النشر | 30–50% | قيود المنصات |
| الأرشيف | 95% | تحقق بشري للحذف |
| المتابعة والتقارير | 90% | أسهل مكسب |

**الأثر الكلي:** 40–60% في أول 3 أشهر، و60–70% بعد التوليف. **لن تصل إلى 90%** بسبب طبيعة المحتوى وحساسية المراجعة.

**أكبر مكسب ليس المونتاج:** بل إنهاء «أين الملف؟ ما حالته؟ من راجعه؟ هل نُشر؟».

## 22. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| انحراف المجلدات عن قاعدة البيانات | مُصالِح دوري + حالة `unknown` + تقرير أسبوعي |
| نسخ ناقص من البطاقة | copy → verify → ثم نقل؛ لا حذف من البطاقة |
| مسارات عربية / طويلة | ASCII slugs + Long Paths + اختبار مبكر |
| فشل الوكيل في منتصف التصدير | `work/` منفصل + نقاط تحقق + `result.json` + إعادة واحدة |
| وظائف طويلة تسدّ الواجهة | طابور + عامل خلفي + SSE |
| ضياع أصل عند الأرشفة | copy → hash → catalog → trash 30 يومًا |
| حذف خاطئ | تأكيد مزدوج + سلة + تدقيق + صلاحية مرتفعة |
| انقطاع الكهرباء | كتابة مؤقتة ثم rename ذرّي + استئناف |
| تغيّر مهارة | `style_version` + هاش الحزمة |
| الاعتماد على شخص واحد | دليل + تشخيص + نسخ احتياطي قابل للاستعادة |
| إرهاق المراجعة | مراجعة مجمّعة + قوائم قصيرة + إشعارات |
| تعريف GPU غير متوافق | Doctor يشخّص ولا يثبّت + توثيق |
| اختلاف جهاز المكتب | `machine_profile` + متطلبات معلنة + وضع وهمي |

## 23. ما لا يجب فعله

1. لا تبنِ الأتمتة داخل المتصفح أو `localStorage`.
2. لا تدع الوكيل ينقل أو يحذف.
3. لا تنشر تلقائيًا.
4. لا تشغّل وظيفتين GPU معًا على 4GB.
5. لا تستخدم مسارات عربية في خط الإنتاج.
6. لا تربط الكود باسم `mreel1`.
7. لا تعتمد على نص المحادثة كمخرَج.
8. لا تبدأ بالأتمتة قبل الكتالوج.
9. لا تحذف من البطاقة أو الهارد دون تحقق هاش.
10. لا تخزّن مسارًا مطلقًا في قاعدة البيانات.
11. لا تعتمد على حرف القرص.
12. لا تضمّن أدوات المونتاج في المثبّت.
13. لا تَعِد بفاعلية 90%.

## 24. نطاق MVP

## 25. قرارات متبقية (تُحسم عند بدء التنفيذ)

## 26. الخلاصة

الفكرة ممتازة ومناسبة لطبيعة العمل: محتوى متكرر، مصادر كثيفة، فريق غير تقني، وحاجة ماسة إلى تتبع. لكن نجاحها يعتمد على **بناء طبقة تشغيل مملة** (قاعدة بيانات، طابور، تحقق، أرشيف) أكثر من اعتمادها على مهارة مونتاج لامعة.

**الترتيب الصحيح للبناء:**

```
الكتالوج والحالة ← الطابور والتحقق ← الوكيل ← الواجهة ← الأتمتة الكاملة
```

لو عكست الترتيب وبدأت بزر «المونتاج التلقائي»، ستحصل على عرض توضيحي جميل لا يستطيع أحد الاعتماد عليه بعد أسبوع.

**أقرب مكسب يستحق البدء:** تطبيق ديسكتوب بسيط + تفريغ البطاقة + الكتالوج + شاشة الوارد. أسبوعان، وينتهي أكبر مصدر للفوضى.
